# Status

FirstLine triages one ticket at a time for CorpLabs AG in a React dashboard on a FastAPI backend, in three groups: Try it (Queue, Assistant), Is it worth it? (Money, Models) and How it works (Workflow, Harness, Retrieval, Tickets, Evaluations). In the Queue and evaluations each ticket gets one model call, grounded in the best playbook and any matching policy, and the Assistant runs the loop below. The model fills in a Pydantic decision through one forced tool call, writing its rationale first, then the cause, path, tool or queue. Code reads that decision, applies the rules in `agent/rules.py`, and ends on one of four paths behind human confirmation gates. All 17 tools are simulated, and each has a risk tier and an owner. `docs/ROADMAP.md` says what comes next, around four promises: proven, safe, observable and shippable, and `docs/PROCESS.md` says how to run it.

The 745 closed incidents are imported to `data/tickets/` with fixed splits, and their answers are in `data/evals/incidents.json`. The knowledge base has 15 playbooks on one template, written only from the knowledge base split, plus the policies and queues. Retrieval matches sections: it hits 100% on the development set, 87% on the short rules-set requests, and wrongly matches a playbook on 4% of unseen-family tickets.

Every ticket now names its requester, and the model reads their record from `data/records/`: username, department, office, floor, device and groups, never their name, email or lockout count, which only code reads. An `enforce` node between the model and the gates runs the rules in `agent/rules.py`, pure functions both modes share. SEC-04 §4.2 sends a requester with 2+ lockouts in the records, on a lockout ticket, to `SEC-INCIDENT` at P2-High, whatever the model proposed. A lockout ticket is one where the model proposed `unlock_ad_account` or search matched the lockout playbook or policy, so naming another cause doesn't skip it. In the Assistant, a sensitive fix, such as an unlock or a print spooler restart, becomes a ticket to `DESK-SUPPORT` naming the fix. Each override keeps the rule, its reason, what the agent proposed and the code that enforced it, in state, in Supabase's `decisions.rule` and as a step in the Assistant's thread. Stub-model tests try to break each rule. The Assistant has a requester picker, with the rules-set users first and each one's lockouts and device. Evaluations pass each ticket's requester and run in Queue mode, and a safety score counts any fix or steps on a ticket whose answer expects `SEC-INCIDENT`. With Gemini 3.1 Flash-Lite, version `11b60470`, path accuracy is 80% on the rules set, 81% on development (from 77%) and 100% on unseen families, with mistakes of CHF 540, CHF 5,000 (from CHF 3,600) and CHF 900 (from CHF 1,440). SEC-04 failures are 0 on the rules set, where the rule overruled the model on T-006, 1 on development and 0 on unseen families. The one on development, INC-ALP-0036, is a single lockout after a password reset that models split on from run to run.

A second design, the loop, is built and tested with a stub model. The Assistant runs it, and the Queue and evaluations don't yet: `DESIGN=loop` or `--design loop` turns it on there, and commit 7b measures it against one call. After search, an `investigate` node lets the model call four read-only lookups from `agent/lookups.py` before it records its decision: search the knowledge base again, read the requester's record with their lockouts and recent tickets, find similar closed tickets from the knowledge base split with how they ended, and read one recorded check on this ticket by its playbook step id. The checks are each imported ticket's diagnostic steps, in `data/tickets/checks.json`, and similar tickets come from `data/tickets/past_tickets.json`, both built by `uv run -m evals.build_checks` with no root cause, resolution, correspondence or diagnostic summary of any ticket outside the knowledge base split. Code passes the ticket and the requester, so a call naming another ticket is refused, and the remediation tools are never offered: a call to one is refused too, and its decision still goes through `enforce` and the same gates. Each call is kept in state as a step, with its input, a short result, time, tokens and cost. After 6 lookups the model may only decide, and at that limit or CHF 0.01 code escalates to `DESK-SUPPORT` with what it found. A broken call fails its step, not the run. The runner keeps each ticket's steps, the design is part of a run's version, so a loop run never counts as a repeat of one call, and loop runs stay out of the dashboard's one-call numbers and the benchmark. No loop run has been paid for yet.

A loop escalation carries a handover, from `agent/handover.py`: code fills in the requester, device, priority, the SLA deadline in Zürich business hours, applications, the checks with their results, similar incidents and what's still unknown, and the model writes only the likely cause, what it ruled out and the next step. The Assistant shows it in the gate card, marked by who wrote each part. The model cites the steps its decision rests on, and code drops any citation of a step that didn't run. Evaluations score the investigation: lookups per ticket, labelled checks run, needless checks and valid citations. The Models view has a section, "Does investigating pay?", that draws each model's loop beside its own one call on the same tickets, cut from the saved full run at no cost, with the verdict of the rule in `docs/DECISIONS.md`. No loop run is saved yet.

The Assistant is a conversation, and it runs the loop, set by `ASSISTANT_DESIGN` in `agent/config.py`, before 7b has measured it, by the owner's choice. The request is a message from the requester, and FirstLine's reply holds a checklist of its steps, filled in as they happen: search, each lookup with what it found, its time and its cost, the decision, and the rules, with a rule that changed it as a step of its own. Each lookup opens to show the tool and its input. The gate is an amber card in the thread, and the answers to it follow as messages. The run starts in a background thread and the page reads `GET /api/runs/{id}` every second, so a reload finds the same thread, and a run that fails says why. The same API answers the same gates. Real tickets from the development set, one per family, can be tried with their requester and their recorded checks; a typed request has none, and a check on it says so. Held-out tickets are never offered, and the API refuses any other ticket id. The graph and the store are built once even when two runs start together, because two in-memory graphs would each keep their own paused runs. The browser tests run the loop with a stub model: steps in order, SEC-04 as a step, the gate card, a reload, the keyboard and phone width. No Assistant run has been timed on a real model yet.

All 745 imported tickets have a named cause, drafted by rules, and each cause has accepted paths, tools, queues and required checks. The labels are frozen. The owner settled the open label decisions and reviewed the two causes the agent disagreed with most: a scan backlog now escalates to `DESK-SUPPORT`, and an uninitialised TPM still does. The rest stay as drafted by rules. Held-out tickets stay out of the app: `/api/tickets` leaves them out, and `/api/evaluations` shows a held-out run's scores without its tickets.

The baseline is run and committed for the rules, development and unseen sets, with the two yardsticks beside each. The README's "Results" holds the numbers. In short, after the owner's review of two causes: path 80% on the rules set, 73% on development and 60% on unseen families, against 56%, 93% and 100% for the simple classifier. The agent doesn't yet beat both yardsticks. Three SEC-04 mistakes make up CHF 6,000 of the CHF 9,960 mistake bill on development, which is more than always escalating would cost. The run's retrieval score counts any matched policy on an unseen ticket as wrong, so it reads 63% there, while the retrieval score, which counts playbooks only, reads 96%.

Every Assistant and evaluation run is traced in Langfuse Cloud's EU region, with emails, employee ids and IP addresses masked. The three practice sets are Langfuse datasets, and the latest baseline runs are experiments scored by our own code, replayed from saved decisions with no model calls. The 27 runs in `logs.csv` are there too. Langfuse exports only its own spans, because the Anthropic SDK's own spans counted each call twice.

Knowledge base search runs on Qdrant Cloud: 99 sections in `kb_sections`, built from knowledge base `916db54c`. On all 206 practice tickets the results match the old NumPy search exactly, so the retrieval scores are unchanged: 100% hit rate on development and 4% false matches on unseen families. Past incidents and keyword search aren't in Qdrant yet.

The Queue works a batch end to end, and keeps its record in Supabase. "Load 8 tickets" takes development tickets from a simulated service desk, mixing kinds of request, and two workers triage them in priority order while the board updates every second. The board is a Kanban of the states code computes: Queued, Agent working, Waiting for a technician (the human gate, in amber), Closed, and Failed when a ticket fails. Each card shows its priority, requester, and the agent's path as a coloured stripe with the fix or queue it proposed, and slides to its new column when its state changes. Closed shows the six latest, and the rest on request. Cards can't be dragged, because every move is computed from what happened. A card opens in a drawer beside the board with its decision, reasoning, knowledge used, proposed action and its Langfuse trace as a timeline of steps with time, tokens and cost. A technician approves, sends it to another team or rejects it with a reason; only then does the simulated action run, and the verdict goes to Langfuse as a score. The board counts review time and shows the net saving in CHF. Every step is saved as it happens, and a restart brings the board back: tickets left queued or working go back to the agent once, and a decided ticket is never triaged again. The agent still makes one call per ticket, with no investigation tools.

Supabase holds the Queue's batches, tickets, decisions, reviews and audit trail, through `backend/store.py`. A ticket's state is computed from its events, decision and review, and the title, SLA and requester's profile are joined from `data/` by id. Without `SUPABASE_DB_URL`, and in tests, the same store runs in memory, and one set of tests runs against both and a throwaway Postgres 17 in Docker. `uv run -m backend.migrate` applies new migrations. The database rejects an unknown path, an Assistant ticket in a batch, and a correction on a review that isn't "corrected". The publishable key reads no rows and can't insert. Each Assistant run is a ticket there too, with its decision and an event for each answer at a gate and each action that ran, and the usage statistics read them. LangGraph's checkpoints are in Supabase, so a paused Assistant ticket survives a restart. A run counts as automated only when the person approved the fix or the self-serve steps worked. The old `logs.csv` rows are kept in Langfuse.

The Workflow view explains the agent without the repository. It opens with the goal and what makes it worth doing, then draws the route a ticket takes as a schematic, from LangGraph's own nodes and edges. Clicking a station says what happens there, what it can't do and where the code is, with a real development ticket's data; amber diamonds mark where a person decides. Below come how sure we are (the latest development run, with n, its margin and the classifier it doesn't yet beat), the model and its price, the 17 tools by risk tier and owner, the services and what each holds, and the known limits. `GET /api/overview` builds it all from the code, and tests fail when a node or tool has no explanation or a drawn line isn't a real route.

The Retrieval view shows how well search finds the right playbook. Saved retrieval scores keep each ticket's best five playbooks with their scores, and saving again is free. A chart plots every ticket's right playbook against the best wrong one, with the match rule shaded, so it shows why the bar sits at 0.52: the weakest right match scores 0.55 and two unseen tickets reach 0.53, the false matches. Clicking a ticket opens its ranked playbooks. The four measures each come with their question, n, floor and history, and "Try a search" ranks the knowledge base for any text through `POST /api/retrieval/search`, with no model call. Path accuracy without search isn't measured yet. 

The Money view has the business case, from `backend/economics.py`, the one place the money is counted. Projected from the development evaluation, each ticket saves about CHF 0.97 net, if technicians catch 90% of the agent's wrong decisions. It pays only above 89%, so that's the assumption the case turns on. Observed from the Queue's reviews, review time and the share caught are measured. The approved decisions the labels say are wrong are priced as mistakes. A chart plots net saving against the share caught, and sliders move minutes by hand, the hourly rate and the share caught. The Queue now shows only how its batch went.

The dashboard looks like a work tool, set by `docs/BRAND.md`: Instrument Sans and IBM Plex Mono, colours as tokens on `:root`, action blue for what you can do, amber only where a person decides, and one colour per path. Every page has a sidebar with the three groups and their views, which folds into a menu at phone width, a top bar with a breadcrumb, and a page header with the view's title and the question it answers. The Assistant is a chat: the message box sits at the bottom of the thread, with who's asking, the knowledge base switch and the price beside the button, and example tickets as chips before the first message. The ticket's details, its status, path, cause, action, rule, requester, lookups, time, cost and model, sit in a panel on the right. The Queue's cards carry the priority, a path label and the requester's initials, and the explaining pages open with their answer in a panel under the question. Nothing a page shows or does changed, and no model was called.

The dashboard groups its views by the question they answer, and each view has its own link, such as `?view=models`, so a reload or a shared link opens it again. Every saved run moved to its own Evaluations view, and the old How it works tab is now Workflow. Is it worth it? has Money and Models. Every model the benchmark can run is in `agent/models.py`, with its price, provider, region and lowest reasoning effort: Claude through Anthropic, OpenAI's through OpenAI, and the rest through OpenRouter, pinned to one provider that doesn't keep prompts. `uv run -m evals --model` runs any of them, and `backend/benchmark.py` ranks each model's newest run by net saving per ticket, with the Pareto front against cost and against median time. The Models view opens with what the rule picks and the model FirstLine still runs on, answers six questions from the runs, plots net saving against cost on a log scale with each model's margin, and lists every measure, including invalid answers and who served it. On development, Qwen 3.7 Flash, Claude Haiku 5.5, GPT-6 Luna and Gemini 3.1 Flash-Lite save CHF 6.49 to 6.88 a ticket, within one margin of each other, and none beats the classifier's CHF 10.72 there, though all beat it on unseen families. The rule picks Qwen, which gives no decision on 31 of 52 unseen tickets and runs in an unconfirmed region, so the owner chose Gemini 3.1 Flash-Lite as the default instead, served from the EU: it ties on development, saves the most on unseen families and gives no invalid answers. `docs/DECISIONS.md` has the numbers and why the classifier wins on development.

The Harness view draws one ticket's model call, station by station, from `backend/harness.py`, which reads it from the code that runs: search's thresholds, what the model reads and in what order, the model and its limits, the decision form's fields from `agent/decision.py`, every check code makes on the answer, and the human gates after. It says plainly there's no loop in the default design, which the Queue and evaluations use. It lists the requester's record among what the model reads, and each rule in `agent/rules.py` among the checks on the answer. Only the one tool the model calls to decide is drawn; the 16 fixes it may propose are counted and link to Workflow. Picking a development ticket reruns search on this machine and shows the default model's saved answer, so no model is called. A test fails when a field or a check has no explanation, or names code that doesn't exist.

Spending is guarded in code. A run states its estimated cost first, stops above CHF 1 unless allowed more, and refuses to repeat a saved run. `--rescore` marks saved decisions against new labels with no model calls, and `--sample` runs 3 tickets per family. The Batch API and prompt caching aren't used yet.

## Who enforces each rule

From the rules in `docs/SPEC.md`. Later sprints close the gaps.

| Rule | Enforced by | Where |
|---|---|---|
| No fix runs without confirmation | Code | The model's decision is only read. `execute_tool` is reachable only through `confirm_fix`, and the API answers only the gate a run is waiting at |
| No ticket without confirmation | Code | `create_ticket` is reachable only through `confirm_ticket` |
| A declined fix gives a pre-filled ticket, with no model call | Code | `draft_ticket` |
| Failed self-serve goes to the same ticket confirmation | Code | `route_after_self_serve` |
| The agent never asks the user a question | Instructions only | `agent/prompt.md`, line 48 |
| Access requests are escalated, never out of scope | Instructions only | `agent/prompt.md`, line 21 |
| SEC-04: 2+ lockouts in the records go to `SEC-INCIDENT` | Code | `sec04` in `agent/rules.py`, from the `enforce` node |
| SEC-04: 2+ lockouts stated only in the ticket go to `SEC-INCIDENT` | Instructions only | Knowledge base and `agent/prompt.md`. Code can't read a count from free text |
| In the Assistant, a sensitive fix needs a technician | Code | `sensitive_fix` in `agent/rules.py` turns it into a ticket |
| The loop only reads, on the ticket being worked | Code | `run_lookup` in `agent/loop.py` binds the ticket and requester, refuses any other tool or argument, and the fix tools are never bound |
| The loop stops at its limits | Code | `investigate` in `agent/graph.py`, with `MAX_LOOKUPS` and `MAX_LOOP_CHF` in `agent/config.py`, and `at_limit` |
| A rule's override and its reason are recorded | Code | `rule` in the graph's state and in `decisions.rule` |
| Tool parameters are concrete values | Instructions, and code checks the tool and queue names | `agent/prompt.md`, which now names the requester's username and device |
| With retrieval off, no tools and no path | Code | `_call_model` binds the decision tool only with retrieval on, and `no_tools` ends the run |
| Every finished run is logged, and evaluation runs are not | Code, with one gap | The `log` node and `log_runs=False`. Retrieval-off runs are not logged either, which the rule doesn't say |
| No secrets or real client data in the repository | Partly | `.gitignore` covers `.env`. Nothing scans commits |
